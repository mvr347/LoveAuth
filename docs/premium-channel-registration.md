# Регистрация канала premium-проверки

Исправление от 15.11.2026 относительно `490fbf8`.

`ServerChannel` передаёт LoveAuth принятый дочерний канал. Его регистрация в рабочем
Netty event loop может быть отложена другими обработчиками. Прежний код вызывал
`child.eventLoop()` сразу после `fireChannelRead`, хотя сам факт передачи сообщения
не гарантирует завершения регистрации. Так возникает `channel not registered to an
 event loop`; стек сам по себе не доказывает ошибку в Vesuvio.

Теперь до передачи незарегистрированного канала добавляется `ChannelInitializer`.
Он получает event loop только после назначения при регистрации и ставит установку
login-перехватчика в очередь после инициализации серверного pipeline. Простого
`if (!isRegistered()) return` нет: оно пропускало бы premium-проверку для штатно
ожидающего регистрации соединения.

Перед отложенной установкой проверяются включённость менеджера, регистрация и
открытость канала. Для уже зарегистрированных каналов установка планируется после
передачи вниз по pipeline. Закрытие event loop при планировании обрабатывается как
остановка соединения. Временный initializer удаляется самим Netty. Повторная установка
login-перехватчика исключена. Снимок NMS handles и синхронизация установки с shutdown
не дают отложенной задаче добавить перехватчик после отключения менеджера.

## Проверка

Java 25, `mvn verify`: 105 тестов, ошибок и пропусков нет.

Четыре новых проверки используют реальные Netty LocalChannel/DefaultEventLoopGroup
и EmbeddedChannel: отложенная регистрация с наличием серверного обработчика и
исполнением на дочернем event loop; отключение до регистрации; закрытие канала
нижним обработчиком; прозрачная передача сообщений при выключенном hook.

Живой premium/offline handshake на Paper/Purpur с Vesuvio не проверен. После установки
JAR и полного перезапуска проверить оба типа входа, отмену подключения и остановку
сервера во время подключения. Изменения настроек не требуются.
